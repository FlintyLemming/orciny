§01

产品概述

1.1 一句话定位

Orciny 是一个自托管的 Coding Agent 机队中台：一个 hub 管住你所有机器上的 Coding Agent 配置，顺带看清它们的用量和订阅余额。

类比：beszel 之于服务器监控，Orciny 之于 Coding Agent 管理。

1.2 背景与要解决的问题

一个重度 Claude Code 用户通常拥有多台 Linux/macOS 机器（工作站、笔记本、家里的 Mac mini、云上 VPS），并同时持有多个 AI Coding 订阅（Claude、GLM、Kimi、火山方舟……）。由此产生三个长期痛点：

  • 配置漂移：~/.claude 下的 settings、CLAUDE.md、skills、agents、MCP 声明在各台机器上各自演化，好用的改动留在一台机器上，坏掉的配置不知道何时引入。
  • 用量黑盒：Token 消耗分散在每台机器的本地会话文件里，没有跨机器视角。
  • 订阅分散：多家 Coding Plan 的余额要逐家查看；部分服务只能在装有本地凭据的机器上查询。

现状方案（rsync 脚本、Syncthing、git dotfiles、各家独立 usage agent）都是单点的、无状态面板的、各管一段的；Anthropic 官方无原生多机同步（截至 2026-07 至少 4 个 open feature request）。论证详见构思报告。

1.3 设计哲学

不接管 Agent 执行，只统一治理配置与观测。Coding Agent 仍在每台机器本地运行；Orciny 决定的是：每台机器用什么配置、装什么 skills、数据汇总到哪里看。Orciny 永远不站在模型请求链路上。

个人版特有的第二哲学：漂移不是违规，是创作。个人在机器上顺手改配置、装插件、写 skill 是主要的创作方式。核心交互「收编」（把某台机器的本地改动一键提升为全机队新基线）就是为此设计的。

1.4 目标用户

层级用户需求特征优先级
P0项目作者本人多台 Linux/macOS + 多订阅，全部痛点的原型MVP 唯一服务对象
P1同类个人开发者self-hosted / homelab 人群 + 重度 Coding Agent 用户开源发布目标
P2微型团队（2–10 人）共享 skills / 配置基线，不需要 RBAC 与审计v2
P3企业治理、合规、多租户不承接，导流 leycode

1.5 非目标（范围护栏）

  • 不做模型路由 / API 网关——不站在请求链路上。
  • 不做 GUI 客户端——agent 无界面，一切交互在 hub Web UI。
  • 不做会话执行编排——不派任务、不开会话、不做任务看板。
  • 不做企业治理——无多租户 RBAC、无合规审计；单管理员起步。
  • Windows 缓做——WSL 场景由 leycode-client 覆盖；首发 Linux + macOS。

§03

系统形态与架构

3.1 组件

组件形态职责
Hub
orciny		 Go 单二进制，PocketBase 内核（内嵌 SQLite、认证、realtime、admin、备份），Web UI（React）编译内嵌。docker run 一行或直跑；数据 = 一个目录。 配置集存储与版本管理、下发调度、漂移收件箱、凭据库、用量与订阅聚合、fetch 型采集器、Web UI、（v1）告警
Agent
orciny-agent		 Go 单二进制，无界面，systemd（Linux）/ launchd（macOS）常驻；最小 CLI。 注册与心跳、配置落盘与 apply 回执、漂移侦测与上报、会话 JSONL 解析上报、local 型订阅采集、自更新

3.2 连接模型（F1）

  • agent 主动外拨 hub 的 WebSocket 端点，长连接保持；断线指数退避重连。
  • 首次接入：Web UI 生成一次性注册 token（限时、单次）→ orciny-agent enroll；agent 生成密钥对，指纹绑定机器身份，token 即焚。
  • 在线状态：长连接存续即在线；心跳 30s（可配）。下发：hub 经长连接即时推送信号，机器秒级对齐。
  • TLS：hub 假定部署在反向代理后（Caddy/Nginx/Traefik），文档给标准配置。
  • 预留：HTTP 长轮询降级通道（协议形状与 leycode 对齐）不进 MVP，接口层留位。

3.3 数据流（四条）

  1. 配置下行Web 编辑 → 发布 Revision → hub 推送信号 → agent 拉取快照 → 落盘（凭据/变量注入）→ apply 回执上行。
  2. 漂移上行agent 监视受管路径（fs 事件 + 定时哈希对账）→ 差异摘要上报 → 收件箱 → 收编 / 恢复 / 忽略；收编则物化为新 Revision 并向其余机器下发。
  3. 用量上行agent 增量解析本地会话 JSONL → 聚合为 UsagePoint 批量上报（含首次历史回灌）。
  4. 订阅采集fetch 型 hub 定时拉取；local 型 agent 本机执行（本地凭据不出机器，只上报结果）；push 型外部进程向 hub HTTP 端点推送。

3.4 部署形态

场景形态
推荐内网或 VPS 上 docker compose up -d（hub）+ 各机器一行安装脚本（agent）
最小hub 单二进制直跑（个人内网，SQLite 文件即全部状态）
备份PocketBase 自带备份（本地目录 / S3 兼容存储），一键恢复
§04

功能规格

4.1 机器管理

接入流程

  1. 生成注册 tokenWeb UI「添加机器」→ 一次性 token（默认 15 分钟有效）+ 拷贝式安装命令 curl -fsSL https://<hub>/install.sh | sh -s -- --token <t>。
  2. 安装与注册脚本探测 OS/arch → 下载 agent → 写 systemd/launchd 单元 → enroll → 上线。
  3. 首报hostname、OS/arch、agent 版本、探测到的 Coding Agent 工具及版本（MVP：Claude Code）。

机器列表与详情

  • 列表列：备注名、在线状态、配置集与对齐状态（已对齐 / 待应用 / 漂移 n 项 / 应用失败）、agent 版本、Claude Code 版本、最后心跳。
  • 行内操作：立即同步、查看漂移、暂停管理（保持连接但不应用下发）、移除（吊销指纹，agent 侧保留本地配置不清理）。
  • 详情页：apply 回执历史、本机漂移记录、机器变量编辑、本机用量速览。
  • agent 自更新：hub 持有目标版本，agent 收通知后自替换重启（beszel 同款）；可全局关闭。

4.2 配置集与版本

  • 结构：受管清单（manifest）+ 文件树 + 凭据/变量引用。MVP 为单层（无继承/叠加）；多机差异走「机器变量 + 凭据引用」；配置集可克隆；继承/叠加层留 v2。
  • 指派：一台机器同一时间指派一个配置集；一个配置集可覆盖多台机器。配置集级「暂停下发」开关（对齐 leycode distribution_enabled 语义）。
  • 版本：发布 = 不可变快照 + checksum；可浏览、diff（文件级 + 行级）、一键回滚（回滚即发布内容等于旧版的新版本，历史不可变）。编辑在草稿态进行，发布前预览 diff。
个人版关键路径 · 导入向导 首台机器接入后引导「把这台机器现有的 ~/.claude 采集为初始配置集」：agent 按默认 manifest 采集 → Web 呈现清单勾选纳管范围 → 敏感项检测（识别 settings env 中的 API key，引导抽取为凭据占位符）→ 生成 v1 并标记该机已对齐。后续机器可选「应用现有配置集」或「保持现状（仅观测）」——后者允许纯用量/订阅场景的机器接入。
  • 编辑器：文件树 + 等宽文本编辑；JSON 语法校验；settings.json 的表单辅助（MVP 可先纯文本）；{{cred.*}} / {{var.*}} 自动补全与未定义引用告警。
  • 发布校验：JSON 合法性、凭据引用可解析、路径安全（禁 .. / 绝对路径 / 符号链接逃逸）。

4.3 受管范围与 Manifest

类别路径策略
纳管（默认）settings.json整文件受管，env 中敏感值以凭据占位符表达
纳管（默认）CLAUDE.md · agents/** · commands/** · skills/** · keybindings.json整文件受管
纳管（键级）~/.claude.json 的 mcpServers键级受管：该文件混有运行时状态，agent 只重写受管键，其余原样保留
恒排除projects/ · todos/ · shell-snapshots/ · statsig/ · 缓存永不采集、永不下发、永不上传
恒排除.credentials.json（OAuth 登录态）机器私有；local 采集器仅本机读取，内容不上传

设计原则：宁可少管，不可误管。未在 manifest 中的路径 agent 一概不触碰；排除规则恒定不可去除。

4.4 漂移与收编（C1 · 本产品的灵魂交互）

  • 检测：文件系统监视 + 周期性哈希对账（默认 5 分钟兜底），与「已应用版本」比对；上报路径、变更类型、脱敏后的内容 diff。
  • 收件箱：全局待处理队列，每条漂移显示来源机器、文件、diff 预览。三个动作：
    • 收编 Adopt——以该机现状生成新 Revision，自动下发其余机器；支持多条漂移合并、跨文件打包收编。
    • 恢复 Restore——指令该机丢弃本地改动回到基线。
    • 忽略 Ignore——路径加入该机忽略清单（局部放行）。
  • 冲突提示：两台机器对同一文件各有漂移时，收编任一台会覆盖另一台——UI 显式警告并展示三方对比（基线 / 机器 1 / 机器 2）。
  • 自动收编规则（路径级）：如 skills/** 设自动收编（本机新写的 skill 直接同步全机队），settings.json 必须手动。默认全部手动，用户逐步放开。

4.5 凭据与机器变量

  • 凭据库：秘密永不进入配置版本；配置内写 {{cred.<name>}}，agent 落盘时换取真实值注入，文件 0600。hub 侧 AES-GCM 加密落库（主密钥来自 env/密钥文件）；Web 只显示名称与末四位；轮换不产生配置新版本，hub 通知受影响机器重注入；凭据页显示引用计数防误删。
  • 机器变量：机器级 KV（如 workspace_root），配置中 {{var.<name>}} 引用；内置 {{machine.name}} / {{machine.os}}。用途：同一配置集覆盖多机时表达小差异，避免为 10% 的差异克隆整个配置集。

4.6 用量观测（D1）

  • 采集：agent 解析 ~/.claude/projects/** 会话 JSONL——增量读取（文件位点）、消息级去重（uuid）、compact/重排容错（管道移植自 leycode-client sessionlog）；首次接入历史回灌。MVP 只上报聚合数据，不上传会话内容本体。
  • 模型：UsagePoint = date × machine × tool × model → input / output / cache_read / cache_write（+ 可选 reasoning）。成本估算基于内置可编辑定价表，标注「等效估算」。
  • 面板：趋势（7/30/90 天）、按机器堆叠、按模型分布、成本开关；口径与本机 ccusage 对齐（同源解析，数字应一致）。
  • v1 预留 · OTel：agent 内置轻量 OTLP 接收端，Claude Code 原生遥测经 localhost 汇入；所需 env 恰好由配置集下发注入——自闭环。

4.7 订阅余额（E1 · 全量 Go 化）

执行位置覆盖服务机制
fetch 型（hub）GLM/bigmodel（含国际版）、Kimi、火山方舟、Sub2API/Codex 中转、ZenMux、华为云、AIPing、Antigravity（API 模式）hub 每 30s 并发刷新；单实例失败不影响其他；连续失败前两次沿用旧值（沿用 ai-plan-insight 容错语义）
local 型（agent）Claude 订阅（本机 OAuth 凭据调官方 usage 接口）、Cursor、Grok、MiMo、Antigravity（本地模式）本地凭据不上传，agent 本机调用后仅上报结果；执行机器可指定或自动（有凭据者执行）
push 型（外部）任意来源HTTP 端点，wire 兼容 ai-plan-insight 现有 payload——移植期的桥 + 长期生态接口
  • 模型别名归并（model_aliases）与来源存活告警（24h 沉默）照搬原语义。
  • 移植策略（E1 风险控制）：按你 config.json 实际启用的实例排序，先自用后长尾；每家以 ai-plan-insight 现网数据对照验收；自用实例 100% 移植且对照一致后 Python 才下线，push 兼容端点长期保留。
  • 面板：卡片墙（「服务名 · 标签」心智）+ 30 天趋势 + 阈值标色 + 来源健康。

§05

Agent 设计（无界面）

职责边界——只做五件事：连接与心跳、配置落盘与回执、漂移侦测、本地数据采集（JSONL + local 采集器）、自更新。不开端口对外服务（除 v1 可选的 localhost OTLP 接收端）。

本地布局

~/.orciny/
├── agent.yml        # hub 地址、机器标识（安装时生成，一般不手改）
├── identity/        # 密钥对与指纹（0600）
├── state.json       # 已应用版本、文件位点、忽略清单（0600）
└── logs/            # JSON lines，保留 14 天，token 一律脱敏

CLI 子命令

命令作用
orciny-agent enroll --hub <url> --token <t>注册接入
orciny-agent status连接状态、已应用版本、待处理漂移
orciny-agent sync立即拉取并应用
orciny-agent drift本机漂移清单（含 diff）
orciny-agent pause / resume暂停/恢复配置管理（数据采集不停）
orciny-agent version / update版本与手动更新

行为准则

  • 宁可不动，不可写坏：apply 前快照备份（本地保留最近 N 版），失败自动回滚并上报。
  • 所有落盘操作幂等；agent 崩溃/断网不影响本机 Coding Agent 正常使用——Orciny 不在关键路径上。
  • 资源目标：常驻内存 < 30MB，空闲 CPU ≈ 0，二进制 < 30MB。

§07

协议与 leycode 对齐（A1）

对齐原则：概念与语义对齐，wire 不强求一致。状态机（draft → publish → apply → ack → drift）、幂等语义、checksum 口径与 leycode 相同；传输载体与字段细节允许不同，命名统一 camelCase。目的：保留远期 A3（Orciny 内核 + leycode 企业外壳）与数据互通的可能性。

概念映射表

leycodeOrciny备注
Profile（base/group 两层）ConfigSet（单层）Orciny 用变量+凭据表达差异，暂无层级
Revision + checksum + 发布物化Revision + checksum语义一致
agent_device_bindings（多绑定）Assignment（一机一集）有意简化
distribution_enabled 下发开关「暂停下发」语义一致
注册码 + 设备指纹一次性 token + 密钥指纹语义一致
apply 回执 / 审计留痕apply 回执 / events 事件流弱化为事件流

§08

安全与隐私

威胁模型（简表）

威胁对策
注册 token 泄露一次性 + 15 分钟 TTL + 使用即焚；Web 可撤销未用 token
agent 身份冒充密钥对指纹绑定；吊销即断
hub 数据库泄露凭据 AES-GCM 加密，主密钥不在库中；会话内容根本不采集（MVP）
传输窃听反向代理 TLS；文档默认 HTTPS，HTTP 仅限内网明示
agent 写坏本机配置manifest 白名单 + 路径安全校验 + apply 前快照 + 失败回滚
凭据在下游泄露落盘 0600；日志全链路脱敏；Web 只显末四位

隐私立场（写进 README 的承诺）

  • 数据不出你的 hub：无厂商遥测、无 phone-home；版本检查可关。
  • 最小采集：会话内容 MVP 不上传（仅聚合数字）；v2 会话检索为显式 opt-in 且支持路径级排除。
  • 本地凭据不动：.credentials.json 等 OAuth 登录态永不上传，local 采集器只在本机使用。
  • 开源发布随附《安全模型》文档（本节展开）。

§10

MVP 范围与里程碑

MVP = 四件事：机器清单与在线状态 · 配置闭环（导入/下发/漂移收编）· Token 用量聚合 · 订阅余额面板。里程碑按序不按期，每个以真实机队验收。

里程碑内容验收标准（对作者本人）
M0 · 骨架hub 可跑（docker+二进制）、enroll、WS 心跳、机器列表与在线状态、设置页雏形≥3 台真机接入；杀 agent/断网后状态与重连表现正确
M1 · 配置闭环导入向导（含敏感项抽取）、编辑器、发布/diff/回滚、下发落盘回执、漂移收件箱（收编/恢复/忽略）、凭据库与变量、快照回滚主力机导入成配置集；全机队对齐；任一机器改 CLAUDE.md / 新增 skill 能被收编并同步；apply 失败自动回滚
M2 · 数据面JSONL 解析上报+历史回灌、用量页；采集器框架 + 自用 provider 全部移植 + push 兼容端点；订阅卡片页用量数字与本机 ccusage 一致；ai-plan-insight 可下线（自用实例 100% 移植并对照验收）
M3 · 毕业与发布全机队迁移、旧方案下线；安装体验打磨；双语 README、安全模型文档、截图与 demo连续 30 天全机队由 Orciny 管理且无手工 ssh 改配置 → 公开发布

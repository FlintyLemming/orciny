§01

结论先行：有没有搞头

判断：有搞头，值得做——前提是把范围卡死在「配置 + 观测」。

这个项目在三个维度上的价值并不均等，分开评估更诚实：

9/10
自用价值 — 第一天就解决你自己的真实痛点
7.5/10
开源影响力 — 需求已验证、形态空缺、有先例
3/10
直接商业化 — 个人工具付费转化极低

支撑判断的四个事实（详细论据见 §03）：

  • 需求真实且官方未满足。Anthropic 仓库至少四个 open 状态的 feature request 在要「跨设备同步 ~/.claude」，社区里 rsync 脚本、Syncthing 挂载、git dotfiles、加密云 CLI 等 DIY 方案层出不穷——痛点广泛存在，但没有一个「自托管 + 面板 + 在线状态 + 用量」的完整形态。
  • 参照物已经成功。beszel 用「轻量自托管 + hub/agent + 好看面板」在两年内做到约 2.3 万 star，证明这个产品气质在 self-hosted 社区能起量；ccusage 等 Claude Code 周边工具则证明这个品类自带流量。
  • 你有不对称优势。这个项目 80% 的难点——配置物化与回执对账、漂移检测、会话 JSONL 解析、多工具适配器、十几家订阅抓取——你在 leycode 两个仓库和 ai-plan-insight 里已经各解决过一遍。别人从零起步，你是做减法。
  • 有天然的差异化切口。海外没有任何工具覆盖 GLM / Kimi / 火山方舟这类中文 Coding Plan 的订阅聚合；ai-plan-insight 并入后，Orciny 在中文社区有独占卖点。
最大的反方论点 Anthropic 随时可能上线官方 cloud sync（相关 issue 热度很高）。对冲方式写在 §08：多工具支持、self-hosted 隐私立场、以及「第三方中转 + 多家订阅聚合」这类官方永远不会做的部分。结论：官方 sync 会削弱「配置同步」单点卖点，但打不掉整个形态。

§04

产品定位与边界

一句话定位：自托管的 Coding Agent 机队中台——一个 hub 管住你所有机器上的 Coding Agent 配置，顺带看清它们的用量和订阅余额。

目标用户（由近及远）

  • P0 · 你自己：多台 Linux/macOS 机器 + 多个订阅（Claude / GLM / Kimi…），配置漂移、用量分散。第一里程碑只服务这一层。
  • P1 · 同类个人开发者：self-hosted / homelab 人群 + 重度 Claude Code 用户，§03 证明这个群体存在且在自己造轮子。
  • P2 · 微型团队（2–10 人）：不需要 RBAC 和审计，但想共享 skills、CLAUDE.md 约定和配置基线。
  • P3 ·（远期）企业：不由 Orciny 承接，导流给 leycode——「团队大了？看这边」。

设计哲学（继承 leycode）

「不接管 Agent 执行，只统一治理配置与观测。」Agent 仍在本地跑，Orciny 决定的是：每台机器用什么配置、装什么 skills、数据汇总到哪里看。

明确不做（范围护栏，也是与红海的分界线）

  • 不做模型路由 / API 网关——不站在请求链路上（claude-code-hub 类产品的地盘，且引入可用性责任）。
  • 不做 GUI 客户端——agent 无界面，systemd / launchd 常驻，一切交互在 hub 的 Web UI。
  • 不做会话执行编排——不派任务、不开会话、不当「任务调度台」（Multica / vibe-kanban 们的红海）。
  • 不做企业治理——无多租户 RBAC、无合规审计（那是 leycode）。单管理员起步，微团队最多加「成员只读/可编辑」两档。
  • Windows 缓做——WSL 场景 leycode-client 已覆盖，Orciny 首发 Linux + macOS。

管什么、不管什么（~/.claude 的选择性管控）

纳入管控（配置集）永不纳入单独通道
settings.json（permissions / hooks / env）、CLAUDE.md、agents/、commands/、skills/、keybindings.json、MCP 服务器声明 会话历史 projects/、todos/、缓存与遥测状态、.credentials.json（OAuth 登录态，机器私有） API Key / Token 走凭据库：版本库里只存占位符，agent 落盘时注入真实值（leycode 4b 已有同款实现），换 key 不产生配置版本
§05

核心业务流

Day-1：从零到全机队上线

  1. 起 hub一条 docker run（或单二进制直跑），打开 Web UI 设好管理员。
  2. 从现状导入在第一台机器装 agent 时，引导「把这台机器现有的 ~/.claude 采集为初始配置集」。个人场景是「先有配置、后有中台」，与企业自上而下相反——这个导入向导是体验成败的关键。
  3. 其余机器一行接入curl 安装脚本 + 一次性注册 token，agent 以 systemd/launchd 常驻，外拨连接 hub，机器列表即刻显示在线状态、agent 版本、Claude Code 版本。
  4. 下发对齐把配置集指派给各机器，agent 落盘、回执；面板显示每台机器「已对齐 / 待应用 / 漂移」。
  5. 数据自动汇入agent 顺带解析本地会话 JSONL 上报 token 用量；订阅抓取器按配置拉取各家余额。首页 = 机器状态 + 用量趋势 + 订阅卡片。

日常循环：改配置的两条路径

  • 面板改：Web 上编辑配置集 → 发布新版本 → 全机队秒级对齐（长连接推送）。
  • 机器上改（个人场景更常见——顺手 /config、装了个插件、写了个 skill）：agent 侦测到本地与已发布版本的差异 → 面板出现漂移提示 → 一键「收编为新版本」（这台机器的改动成为新基线，同步给其他机器）或「恢复」（回到基线）。可对某类路径设自动收编。

「收编」是 Orciny 与企业中台在产品语义上的分水岭：企业把漂移当违规，个人把漂移当创作。详见决策 C。

业务对象（一览）

Machine（机器）· ConfigSet（配置集）· Revision(版本) · Assignment（机器⇄配置集指派）· DriftEvent（漂移）· Credential（凭据）· UsagePoint（模型用量点）· SubscriptionCard（订阅卡片）· Alert(告警)。前六者来自 leycode 模型的裁剪，后三者来自 ai-plan-insight 的并入。

七组选型决策

每组给出可选方案与我的推荐。点击方案卡可记录你的倾向，页面底部（§10）汇总成结果，可一键复制发回给我。工作量标记：S ≈ 数个周末 · M ≈ 一两个月业余 · L ≈ 一个季度以上。

决策 A

与 leycode 的关系

新项目和已投入大量工作的企业版是什么关系？决定仓库、品牌与长期维护结构。

A1 推荐
独立新项目，协议对齐
新仓库新品牌；agent 协议、Profile 概念与 leycode 有意同构，代码选择性搬运，不共享运行时。
  • 轻装上阵，开源干净（leycode 耦合企业内部 newapi/Casdoor，不宜直接开源）
  • 两边受众、技术气质本就不同，分开反而互不拖累
  • 协议同构给未来互通留门
  • 部分逻辑双份维护
额外成本：协议对齐的自律
A2
leycode 同仓双形态
在 leycode 里加「个人版」部署形态，一套代码两种打包。
  • 不分叉，一处修两处得
  • 栈不匹配：个人版要单二进制+SQLite，leycode 是 Node+PG+企业依赖
  • 开源即暴露企业实现；个人版永远被企业需求拖着走
工作量：M（改造）+ 长期约束
A3
Orciny 为开源内核，leycode 重构为企业外壳
倒置 open-core：新项目是核心，企业能力叠加其上。
  • 终局最优雅，一个内核两条产品线
  • 现在做代价大：leycode 已有生产部署，重构风险高
  • 在想清楚 Orciny 形态前就绑死架构，为时过早
工作量：L（现在）；可作为远期方向
推荐 A1：独立起步 + 协议自律。A3 不是被否决而是被推迟——A1 把协议对齐做好，两年后若 Orciny 成立，随时可以走向 A3。
决策 B

技术底座

hub 用什么写？这决定部署形态，而部署形态就是 self-hosted 产品的第一印象。

B1 推荐
Go 全家桶：PocketBase hub + Go agent
beszel 同构：hub = PocketBase（内嵌 SQLite、auth、realtime、admin）+ 内嵌 React 前端，单二进制；agent 纯 Go。
  • 部署气质 = beszel：一个文件跑起来，内存以 MB 计，self-hosted 社区审美
  • leycode-client 的 Go daemon（applier/sessionlog/poller）近乎直接移植
  • 有 beszel 整个仓库当施工参考
  • hub 业务逻辑（Profile/发布/对账）要从 TS 重写为 Go
工作量：M
B2
裁剪 leycode-hub + 新 Go agent
把 Fastify+Drizzle 的 hub 砍掉企业模块、PG 换 SQLite，agent 另写。
  • 复用最多现成业务代码与测试
  • 部署要 Node 运行时或较大镜像，与「轻」的定位相悖
  • 从企业代码里做减法，砍耦合的工夫未必比重写省
工作量：M（省在逻辑，费在解耦）
B3
纯 Go 自研 hub
chi/echo + SQLite 自己搭，不依赖 PocketBase 框架。
  • 零框架绑定，长期自由度最高
  • auth、realtime、admin、备份全部自己造，MVP 周期显著拉长
工作量：L
推荐 B1：你要的形态（参考 beszel）已经替你选好了栈。PocketBase 若日后成为瓶颈，届时业务已验证，迁移是幸福的烦恼。
决策 C

配置同步模型（最核心的产品决策）

「谁是真相」决定整个产品的交互性格。企业答案是「中台是真相」，个人场景没有现成答案。

C1 推荐
中台为准 + 漂移收编
hub 是唯一基线；机器上的改动被侦测为漂移，面板一键「收编为新版本」或「恢复」，可按路径设自动收编。
  • 多机一致性语义清晰，永远知道基线是什么
  • 「收编」把个人的顺手改动变成正式版本——尊重个人工作流而非对抗它
  • 与 leycode 协议天然同构（A1 的对齐要求）
  • 本机改动要多一次确认（自动收编规则可缓解）
复用：leycode 漂移/对账逻辑
C2
机器为准，自动双向
hub 只是同步中继 + 备份，任一台的改动自动成为最新状态（Syncthing 心智）。
  • 最省心，零确认
  • 两台各改一处怎么合？冲突语义天生模糊
  • 错误配置会静默传染全机队，难回溯
  • 与企业协议不同构，A3 的门关掉一半
工作量：M，但边界情况长尾
C3
Git 仓库为准
配置集 = git repo（hub 内建或外部 GitHub），agent 负责 auto-commit / pull。
  • 版本、diff、回滚、历史免费；极客好感度高
  • 合并冲突直接暴露给用户，面板编辑体验要绕着 git 走
  • 秘密管理与 git 历史天然打架
工作量：M
推荐 C1：产品语义用「声明式 + 收编」，底层存储不妨用 git（或 content-addressed 存储）实现版本与 diff——取 C3 的实现红利，不取它的用户心智负担。
决策 D

用量数据采集通道

「数据收集要留扩展余地」——用量数据从哪条管道来？

D1 推荐 MVP
会话 JSONL 解析上报
agent 解析本地 ~/.claude/projects/ 会话文件，增量上报 token 用量（ccusage 思路）。
  • 零配置、可回灌历史、离线补报
  • leycode-client 的 sessionlog 管道是现成的（含 compact 重排、Cursor 双根）
  • 解析逻辑要跟着 Claude Code 版本走（ccusage 同病，社区可分摊）
复用度：高
D2 v1 扩展
OpenTelemetry 通道
利用 Claude Code 原生 OTel 导出，agent（或 hub）内置轻量 OTLP 接收端。
  • 官方支持的标准出口，指标丰富（活跃时长、工具调用等）
  • 协同优势：telemetry env 正好由 Orciny 的配置下发顺手注入
  • 无历史回灌；需改用户 env；实时性依赖会话进行中
工作量：S–M（在 D1 之上叠加）
D3 随决策 E 并入
订阅余额抓取
ai-plan-insight 的 fetch/push 双模式整体并入：hub 拉 API 类（GLM/Kimi/火山…），agent 抓本地类（Claude/Cursor…）。
  • 中文 Coding Plan 覆盖是独占卖点
  • 协议成熟且已在生产运行
见决策 E
推荐 D1 + D3 进 MVP，D2 作为 v1 扩展点——三条通道不互斥，是分期问题而非取舍问题。会话日志「全文」上传（leycode 块八能力）另作 v2 可选开关：跨机器搜索历史会话对个人是杀手锏，但先把用量跑通。
决策 E

ai-plan-insight 合并路径

Python 面板如何进入 Go 新世界？它还在生产运行，迁移不能断档。

E1
一次性 Go 重写
14+ 家 Provider 抓取逻辑全部移植进 hub/agent，Python 项目退役。
  • 终态干净，单一技术栈
  • 一次性移植量大，长尾 Provider 的调试成本高
  • 迁移期你自己的面板断档
工作量：M–L
E2
保留 Python 采集 sidecar
ai-plan-insight 去掉前端，作为采集服务把数据推给 Orciny hub。
  • 几乎零迁移成本，立即可用
  • 永久多一个服务与一个运行时，违背单二进制气质
工作量：S
E3 推荐
协议先行，分阶段吸收
第一步：hub 原生实现 ai-plan-insight 的 push API 兼容层——现有各家 *-usage-agent 与 Python 服务不改一行就能把数据打进来；第二步：按使用频率逐个把 Provider 移植进 Go，直到 Python 退役。
  • 不断档：面板第一天就有数据
  • push 协议兼容顺带成为公开生态接口（第三方可自写 pusher）
  • 移植节奏完全自主
  • 过渡期存在双轨
工作量：S 起步，M 收尾
推荐 E3：把「兼容 push API」升格为产品特性而不只是迁移手段——它让 Orciny 天生就有一个开放的数据摄入口。
决策 F

Agent 连接与安全模型

agent 与 hub 怎么连、怎么信任？家庭 NAT 后的 Mac mini 和云上 VPS 都要能接入。

F1 推荐
agent 外拨 WebSocket
agent 主动连 hub（一次性注册 token + 指纹），长连接推送下发，断线重连。beszel 同款。
  • NAT 友好：机器在哪都能连，hub 无需触达 agent
  • 在线状态、秒级下发天然免费
  • hub 需要一个可达地址（个人场景通常有：内网或小 VPS）
工作量：S–M（beszel 有完整参考）
F2
HTTP 长轮询
leycode 已验证的复合 ETag 长轮询协议直接平移。
  • 实现最简单，协议已被 20+ 集成测试验证
  • 与企业协议完全同构
  • 实时性与在线状态弱于长连接（秒级 vs 轮询间隔）
工作量：S
F3
hub 主动 SSH 连 agent
hub 侧发起连接，agent 监听。
  • hub 不需要公网可达
  • 要求每台机器可被 hub 触达，NAT 场景反而更麻烦
  • 个人机器（笔记本）IP 漂移，管理负担在错的一侧
工作量：M
推荐 F1，接口层留出 F2 作为受限网络的降级路径（两者可共存，beszel 就是双通道）。安全基线：一次性注册 token、agent 指纹绑定、凭据只在下发注入时经手且不落审计、TLS 交给反代。
决策 G

开源与商业策略

§01 的三维评分已经给出方向感：这决定投入预期与宣发动作。

G1
纯自用
解决自己的问题就收工。
  • 零维护压力、零宣发成本
  • 浪费差异化资产与已验证的社区需求
机会成本：高
G2 推荐
MIT 开源，社区驱动
英文 README 面向 self-hosted 社区 + 中文 README 面向国内生态，不承诺 SLA，接受贡献。
  • star / 影响力 / 简历价值；Provider 适配这类长尾正适合社区共建
  • 「自托管、数据不出家门」的立场与开源互为背书
  • issue 维护是真实的时间税
附加成本：宣发 + 维护节奏管理
G3
Open-core 收费
个人免费，团队功能（成员、共享库）收费或闭源。
  • 理论上有变现路径
  • 个人工具付费转化极低；付费墙会掐死早期增长
  • 你已经有企业变现载体——它叫 leycode
建议：不设计付费墙，只留 hook
推荐 G2：把「商业化」明确让渡给 leycode（Orciny 页脚一行「Need teams & governance? → leycode」就是全部商业动作）。Orciny 挣的是影响力与入口，不是钱。
§07

MVP 与路线图

MVP 只做四件事（按推荐组合 A1·B1·C1·D1+D3·E3·F1·G2 展开）：

#能力验收标准（对你自己）主要复用
1机器清单与在线状态所有机器一行命令接入，面板可见在线/版本/最后心跳beszel 连接模型
2配置集：导入 → 下发 → 漂移收编从主力机导入现有 ~/.claude；改动可发布到全机队；机器上顺手的改动能被收编或恢复leycode Profile/对账 + client applier
3Token 用量聚合按机器/模型/日查看用量与估算成本，含历史回灌client sessionlog 管道
4订阅余额面板现有 ai-plan-insight 卡片全部点亮，数据不断档push API 兼容层（E3 第一步）

里程碑（按序不按期）

  1. M0 · 骨架：hub 起得来 + agent 注册上线 + 机器列表。（打通 beszel 式管道）
  2. M1 · 配置闭环：导入 / 编辑 / 发布 / 落盘回执 / 漂移收编。（产品成立与否看这里）
  3. M2 · 数据面：JSONL 用量上报 + push API 兼容 + 订阅卡片。（此时可替换线上 ai-plan-insight）
  4. M3 · 自用毕业：你所有机器迁移完毕，旧方案下线 → 打磨安装体验后开源发布。

发布后的扩展序列（预留而不预支）

  • v1：告警通知（订阅阈值 / 机器离线 / 应用失败 → ntfy · Telegram · Bark）；OTel 接收端（D2）。
  • v2：会话日志全文可选上传 + 跨机器检索（leycode 块八移植，个人版杀手锏）；OpenCode / Codex 等多工具适配（AgentAdapter 已就绪）。
  • v3：微团队（邀请成员、共享 skills 库）；与 leycode 的互通/迁移通道（A3 是否启动在此时决策）。
§08

风险与对冲

风险等级分析与对冲
官方推出原生 sync中 四个高热度 issue 意味着 Anthropic 迟早会做「账号级云同步」。对冲：① 自托管隐私立场（不想把 CLAUDE.md 和公司项目路径传给任何云的人群恒在）；② 多工具覆盖（官方只会同步自家）；③ 订阅聚合、第三方中转用量、机队观测是官方永远不做的。官方 sync 出现后 Orciny 的重心自然滑向「观测 + 多工具 + 订阅」，形态仍然成立。
做成红海里的又一个编排工具中 「顺手加个远程开会话」的诱惑会一直存在。对冲：§04 不做清单是护栏——不碰执行链路，这也是与 Multica/agent-fleet 们的清晰区隔。
追版本的维护税中 settings schema、JSONL 格式、各家订阅 API 都会变。对冲：解析层独立成包 + 契约测试；这类长尾正是开源社区最愿意贡献的部分（ccusage、ai-plan-insight 的 Provider 生态已证明）。
个人精力，三线作战高 leycode 尚有客户端收尾（C1/C2），Orciny 是新战线。对冲：① MVP 卡死四件事；② M2 完成即替换 ai-plan-insight——新项目上线同时旧项目下线，净维护面不增反减；③ leycode 与 Orciny 共享协议心智，切换成本低。
秘密管理出安全事故高（影响）/ 低（概率） hub 集中保管各家 API key，一旦泄露伤害集中。对冲：凭据加密落库、版本库只存占位符、agent 侧 0600 落盘（leycode 已有实践）、公开安全模型文档。这是开源前必须过的关，不是 v2 作业。
§09

命名提案

beszel 取自 China Miéville 小说《The City & The City》中的城市 Besźel——两座城市物理上重叠、居民却被训练「视而不见」对方。沿这个思路给出四个候选：

orciny 主推
同书 · 传说中的第三座城

Orciny 是传说里存在于双城「缝隙」中的隐形之城，据说在暗中治理着两座可见的城市——一个不可见的层，治理你所有可见的机器。与 beszel 同宇宙致敬（你的形态参照正是 beszel），拼写独特，六个字母适合 CLI，GitHub / npm 均无重名冲突（已查）。彩蛋空间：数据脱敏开关可叫 unsee（书中「视而不见」的术语）。

uqbar
博尔赫斯《特隆、乌克巴尔、奥比斯·特蒂乌斯》

一部描述虚构世界的百科全书，最终重塑了现实——「配置即真相」的完美隐喻。缺点：有区块链项目重名，Tlön 系词汇被 Urbit 生态占用过。

armada
Miéville《The Scar》· 浮动海盗城

由无数被掳船只拼成的移动城市——「机队（fleet）」的直白隐喻，同属 Miéville 宇宙。缺点：常用词，重名多，搜索引擎不友好。

erewhon
塞缪尔·巴特勒《埃瑞璜》

「nowhere」的变位词，书中「机器之书」章节是最早的机器演化论。文学梗极佳，但七个字母 + 发音不直观（err-e-hwon）。

弃选说明：Breach（同书中跨城执法机构，语义极贴）因在安全语境里是「入侵/泄露」，对一个保管 API key 的工具是灾难性联想，放弃。
